# Домен: прогноз длины ответа LLM

## Постановка

Дана пара «запрос × модель»: текст запроса, имя одной из 13 open-source моделей CASTILLO и длина запроса в токенах этой модели. Нужно предсказать, сколько токенов модель сгенерирует в ответе, а не только точечное значение: для каждой строки требуется `pred`, а также интервал `lo..hi`, который должен накрывать 10–90 % распределения длины.

Метрика — `MAE(pred) + 2·pinball_0.1(lo) + 2·pinball_0.9(hi)` в шкале `log1p(токенов)`, среднее по строкам. Она одновременно штрафует неточный точечный прогноз и плохо откалиброванный интервал. Направление — minimize.

Задача полезна для планирования нагрузки и стоимости вызовов: по запросу заранее оценить, сколько токенов и времени потребует ответ. В CASTILLO есть длины ответов, но нет латентности, поэтому прогноз времени в этот кейс не входит.

## Данные

- 13 моделей: Qwen2.5 7B/14B/32B, Llama 3.1-8B / 3.2-1B / 3.2-3B / 3.3-70B, Gemma-3 4B/12B, Phi-4-mini, Mistral-7B, Ministral-8B, Mixtral-8x7B.
- 11 395 запросов из Alpaca, Dolly, ShareGPT, Apps, BigCodeBench, MBPP и DS-1000.
- На пару «запрос × модель» записано обычно 10 длин ответов; после склейки 207 повторных `sample_id` у части строк стало 20 или 30 длин, у одной — 14.
- Train / public / private: 83 813 / 27 905 / 27 906 строк, 175 / 60 / 59 батчей. Разделение — по семействам похожих запросов, пересечений семейств между split нет.

Данные стохастичны: даже для одной пары длина ответа меняется между генерациями. Поэтому нижняя граница ошибки для любого предсказателя — оракул, который знает квантили собственных ответов строки: MAE `0.152`, полный score около `0.282`. Остаток после хорошей модели — шум самой генерации, а не недоработка признаков.

## Классические подходы

| Подход | Идея | Сильные стороны | Слабые стороны | Оценка на public |
| --- | --- | --- | --- | --- |
| Глобальные квантили | Одна тройка `lo/pred/hi` для всех строк, взвешенно по train | Простой, устойчивый, почти бесплатный | Не учитывает модель, запрос и тип задачи | MAE `0.743`, baseline |
| Квантили по модели | Своя тройка для каждой из 13 моделей | Учитывает разный стиль длины у моделей | Не видит содержания запроса | MAE `0.734` |
| Квантили по модели и источнику | Тройка на пару «модель × источник» | Ловит различия кода, диалогов и инструкций | Источник есть в `meta` train, но это грубая категория | MAE `0.635` |
| Регрессия по признакам | `input_tokens`, длина запроса, модель, источник; квантильная регрессия или бустинг | Интерпретируемо, быстро, легко калибруется | Может не уловить смысл запроса | требует замера |
| kNN по эмбеддингам | Искать похожие запросы в train и переносить их длины | Использует семантику без обучения с нуля | Дороже на CPU, зависит от эмбеддингов и соседей | требует замера |
| Обученная модель длины | Предсказывать распределение токенов по тексту и модели | Потенциально лучший перенос на новые запросы | Нужны данные, риск переобучения и тяжёлый инференс | требует замера |

## Почему задача подходит для арены

Пространство решений большое: признаки, статистики по train, квантильные модели, kNN, эмбеддинги и калибровка интервалов дают разные направления поиска. Метрика полностью программная и дешёвая, LLM в решателе и оценщике не нужна. Данные уже разделены по семействам, а public и private не видны исследователю, поэтому эволюция проверяет перенос, а не запоминание.

## Baseline

Стартовый кандидат — глобальные квантили 0.1 / 0.5 / 0.9 по train: `lo=59`, `pred=367`, `hi=779`. Каждая длина строки имеет вес `1/k`, поэтому строка с 20 или 30 записанными ответами не получает большего веса. Это оптимум среди константных предсказателей для данной метрики и честная нижняя планка для всех дальнейших кандидатов.
